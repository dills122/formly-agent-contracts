# v0.4 Cross-Field Effects and Ordering Research

**Scoped status:** Reconciled research prototype complete; high-level
architecture decision ready; public DTO and production behavior not approved

## Executive conclusion

Angular and Formly can reveal that cross-field behavior exists and can expose
some target-state changes. They do not provide a general application effect
graph. In particular, neither framework can reliably turn an arbitrary
expression function, custom `props.change` property, service call, or one
scenario run into the semantic claim “A loads, filters, clears, or toggles B.”

The recommended direction has two deliberately unequal evidence tiers:

1. A trusted compiler may emit **review scaffolding** from a very conservative
   subset of Formly string expressions and from controlled scenario deltas.
   These records are dependency-only or candidate evidence and cannot authorize
   test ordering.
2. The application explicitly declares **actionable operational effects**
   against stable contract node IDs. These records include trigger, target
   property, effect kind, timing/readiness, condition reference, and ordering.

Opaque behavior is retained as an incomplete-coverage signal, not fabricated
into an edge. When coverage is incomplete, absence of an edge cannot prove that
two fields are independent or that a target is unreachable.

This is a **go** for the ownership split and explicit per-form effect registry.
It is a **no-go** for automatic `loads`/`filters`/`clears`/`toggles` inference.
It is only a **conditional go** for string-reference scaffolding: production
work must use JavaScript-compatible parsing, stable node IDs supplied by the
contract compiler, relative model-scope normalization, and the conservative
refusal rules demonstrated here.

Combined with project-aware configuration and field-type profiles, this design
can address the ordering gaps encountered in testing once implemented:

- project configuration loads the correct form registry, Angular feature
  providers, scenarios, and application effect declarations;
- field profiles explain how individual custom controls are operated and which
  state/readiness capabilities they expose; and
- the per-form effect graph connects stable field instances and declares the
  required ordering.

The spike does not claim browser conformance, production corpus coverage, or a
complete public DTO.

## Decision packet

### Question and owner

Which cross-field dependency and change-effect facts can be extracted from
public Formly configuration, and which must be application-declared?

The repository maintainer owns the decision. This artifact proposes an
architecture and validates a bounded research shape; it does not authorize a
schema or runtime change.

### Why the answer matters

A field profile can explain how to select a product, case type, or table row,
but it cannot say which field must be set first or what must settle afterward.
Typed E2E intent needs trustworthy facts such as:

- selecting product precedes case-type enumeration;
- changing product invalidates or replaces case-type options;
- selecting case type populates another field;
- hiding a field may reset its value under Formly's effective reset policy; and
- an asynchronous effect has a semantic readiness condition.

Guessing these relationships from proximity, labels, callback names, or timing
would undermine the contract's selector- and behavior-honesty guarantees.

### Scope and prohibitions

The spike uses only repository fixtures and the installed Angular 20.3.29,
Formly 6.1.8, TypeScript 5.9.3, and RxJS 7.8.2 stack. It compares:

- explicit application declarations;
- `expressions`, legacy `expressionProperties`, and `hideExpression`;
- function/Observable expressions and `props.change` property existence;
- isolated JavaScript-expression AST analysis;
- controlled Formly scenario differentials; and
- runtime/browser observation as a future evidence tier.

It does not parse `Function.prototype.toString()`, execute callbacks during
declared analysis, call remote providers, inspect private Angular metadata,
analyze whole-project symbols/imports/templates, add a public DTO, or implement
a Playwright wait strategy.

## Method

1. Read the architecture, v0.4 research plan, field-profile result, current
   adapter projection, and synthetic fixture corpus.
2. Inspect Formly 6.1.8's installed declarations and expression extension.
3. Write failing tests for direct references, opaque functions/handlers,
   computed and field-rooted paths, writes, nested functions, JavaScript
   compatibility, Formly expression precedence, model-target expressions,
   dynamic arrays, hooks/validators, scenario loads/clears/structure, duplicate
   IDs, non-JSON observations, explicit endpoints/capabilities/readiness, and
   cycles.
4. Implement the smallest research prototype satisfying those refusal cases.
5. Run two real isolated `FormlyFormBuilder` scenarios varying only the product
   model value and compare normalized field observations.
6. Subject the packet to independent single-model and cross-model adversarial
   review, then narrow unsupported claims and expand negative coverage.

## Evidence

### Documented facts

1. Formly expressions assign a string, function, boolean, or supported reactive
   result to a named field property. Its examples show both string and function
   forms reading model state. Source:
   <https://v6.formly.dev/docs/guide/expression-properties/>.
2. Formly documents `options.fieldChanges` expression events containing the
   affected field, event type, target property, and evaluated value. The event
   does not include an upstream dependency path or an application semantic verb.
   Source:
   <https://v6.formly.dev/docs/guide/expression-properties/#3-get-notified-about-an-expression-changes>.
3. Formly documents reset-on-hide as the default and `resetOnHide: false` as the
   field-level preservation override. Source:
   <https://v6.formly.dev/docs/guide/expression-properties/#2-conditional-rendering>.
4. Formly 6 replaced `expressionProperties` with `expressions` while retaining
   legacy compatibility. Source:
   <https://v6.formly.dev/docs/guide/migration/>.
5. The Formly v6 public API includes expression maps, `hideExpression`,
   `props.change`, hooks, validators, async validators, parsers, and dynamic
   `fieldArray`, but no cross-field effect DTO. Source:
   <https://v6.formly.dev/docs/api/core/>.
6. Angular AOT and language-service tooling analyze Angular and TypeScript
   source for compilation, template checking, diagnostics, and navigation.
   Those documented responsibilities do not constitute an application effect
   graph. Sources: <https://angular.dev/tools/cli/aot-compiler> and
   <https://angular.dev/tools/language-service#how-the-language-service-works>.

### Exact pinned-package observations

The following observations apply to installed Formly 6.1.8, not every version:

1. String expressions are compiled through JavaScript's `Function` constructor
   with `model`, `formState`, and `field` arguments. A TypeScript-only expression
   accepted by a TypeScript parser is not necessarily executable by Formly.
2. Registration order is `hideExpression`, then `expressions`, then legacy
   `expressionProperties`. All write into the same property-keyed internal map,
   so later declarations replace earlier declarations for the same target.
3. The extension records paths for the **target property being assigned**, not
   paths read by an expression. Its private `_expressions[*].paths` data is not
   a dependency graph.
4. A target beginning `model.` is a special model write and may refer to a
   sibling/relative control. The expression-owning field is not automatically
   the target node.
5. Parent hide/disabled state can propagate to descendants. A leaf-only
   observation would omit that inherited effect.
6. Hidden-state processing may unregister and reset controls when the effective
   reset policy permits. Therefore “visibility changed” is distinct from an
   arbitrary application-declared `clears` edge.
7. `props.change` is a callback-shaped property. Custom field templates own
   whether and when they invoke it; property existence does not prove an exact
   runtime trigger.

### Repository observations

1. The current adapter preserves string conditions and reports opaque
   function/async behavior without executing callback bodies.
2. Production node IDs are more precise than dotted Formly keys: they include
   form identity, encoded typed path tokens, positional identity for keyless
   nodes, and deterministic duplicate handling. The spike therefore requires
   the caller to supply stable contract node IDs and does not manufacture IDs.
3. The reconciled prototype accepts normalized `{ nodeId, field }` entries. It
   does not traverse nested groups or dynamic arrays and reports dynamic
   `fieldArray` functions as out of scope.
4. The string analyzer blocks all candidate edges on parse errors,
   TypeScript-only syntax, nested function syntax, or writes to dependency
   roots. It separately reports computed and `field.*` rooted references,
   unsupported target properties, and opaque call semantics.
5. Literal path identity retains string versus numeric segments and distinguishes
   `model.a.b` from `model['a.b']`.
6. Function expressions, Observables, and `props.change` are classified
   separately and never invoked. A static false `hideExpression` produces no
   fabricated function signal.
7. Hooks, executable validators/async validators, parsers, ancestor state
   propagation, model-target expressions, and dynamic arrays produce explicit
   incomplete-coverage signals rather than disappearing.
8. Scenario comparison retains `value → undefined` and
   `undefined → options` transitions as candidates. It rejects duplicate node
   IDs and non-JSON observations and reports added/removed nodes or properties
   as structural unknowns.
9. The real builder test observes both option and visibility changes between
   alpha and beta product scenarios. It does not label the option transition as
   a load or filter.
10. Explicit-effect validation exercises trigger event, target property,
    effect kind, timing/readiness, ordering, declared evidence, opacity,
    endpoint existence, target capabilities, and strongly connected components.

### Inferences

1. A direct JavaScript string reference can be useful review scaffolding after
   its field-relative source path is normalized against the built form tree.
   The reference proves syntactic data access, not polarity, business meaning,
   or interaction ordering.
2. The target property identifies a broad state category—visibility,
   enabled/disabled, required, options, or value—but not `loads`, `filters`,
   `clears`, or `toggles`.
3. A controlled delta establishes that a target observation differed across two
   named scenarios. It does not prove causality or distinguish local filtering,
   remote loading, cache behavior, elapsed time, or another scenario input.
4. Whole-project source and template analysis could produce additional review
   candidates, but aliases, imports, helpers, services, closures, and generated
   code make it unsuitable as automatic semantic authority.
5. Runtime Formly events and browser traces could verify a declared target
   outcome in visited scenarios. They cannot establish global branch coverage
   or safely invent missing operational semantics.

### Unknowns

1. Workplace-corpus proportions of direct strings, opaque functions, handlers,
   hooks, and service-driven behavior are not measured.
2. Production normalization of field-relative `model`/`formState` references,
   repeated rows, parents, and keyless groups is not implemented here.
3. Async readiness vocabulary, errors, cancellation, races, and timeout policy
   remain open.
4. Lazy feature injectors may expose forms/providers absent from a root-only
   compilation host.
5. No browser or `fieldChanges` trace was run in this spike.
6. Cycle severity and convergence policy are undecided; deterministic SCC
   reporting does not prove a cycle is invalid.

## Comparison matrix

| Approach | Safe output | Actionable ordering? | Principal boundary |
| --- | --- | ---: | --- |
| Explicit application effect | Exact declared trigger, target, kind, timing/readiness, ordering | Yes, after validation | Declaration may drift; needs conformance |
| Formly direct string reference | Dependency-only source path plus known state target | No | Relative scope, supported grammar, no semantic verb |
| Function/Observable expression | Target property plus opaque dependency signal | No | Closures, services, async work, arbitrary code |
| `props.change` property | Property-existence signal only | No | Custom widget may not invoke it |
| Isolated expression AST | Conservative lexical read candidates and refusal diagnostics | No | Not symbol/import/template analysis |
| Whole-project source/template analysis | Potential review scaffold | No | Not prototyped; call-graph and semantic ambiguity |
| Controlled Formly scenarios | Scenario-specific changed target properties | No | Correlation, scenario completeness, async settling |
| Formly runtime events | Future observed target/property/value trace | No by itself | No source/cause; executed states only |
| Browser trace | Future rendered outcome for visited steps | Only validates declarations | Visited states, timing, unrelated effects |

## Candidate authoring model

The prototype exercises this decision-bearing shape, but the names and exact
schema remain candidates:

```ts
interface DeclaredFieldEffect {
  id: string;
  trigger: {
    nodeId: string;
    event: 'valueChanged' | 'selectionChanged';
  };
  target: {
    nodeId: string;
    property: 'options' | 'value' | 'visibility' | 'enabled' | 'required';
  };
  kind: 'loads' | 'filters' | 'clears' | 'toggles' | 'controls-state';
  timing: {
    mode: 'sync' | 'async' | 'unknown';
    readinessId?: string;
  };
  conditionRuleId?: string;
  ordering: 'source-before-target' | 'none';
  evidence: 'declared';
  opacity: 'transparent';
}
```

An async effect requires a serializable `readinessId`. The field profile owns
the readiness capability and assertion surface; the executable driver only
implements an already-validated capability. Project configuration references
profiles and effect data but does not embed executable readiness semantics.

Opaque behavior uses a separate record containing declaration location,
whatever target state is actually known, evidence kind, reason, unknown
dimensions, and an analysis-level coverage state. It is not inserted into the
actionable graph with imaginary endpoints.

This coverage boundary is required for reachability: when analysis is
incomplete, typed intent may validate an explicitly declared path, but it may
not use edge absence to prove “unreachable” or “independent.” The prototype
does not implement reachability itself.

## Configuration and ownership fit

### Root configuration

Root configuration owns workspace policy, not application relationships:

- enable/disable conservative source scaffolding;
- choose whether incomplete effect coverage warns or fails a release gate;
- select cycle diagnostic policy;
- require effect/profile schema versions; and
- decide which controlled evidence tiers are retained.

### Project and form registration

Project configuration loads the application truth:

- the Angular/Formly compilation host and relevant lazy feature providers;
- the form registry and canonical stable node namespace;
- application-owned serializable effect declarations per form;
- synthetic scenario inputs; and
- referenced field profiles/readiness capability IDs.

Effects should live beside form registration or in a versioned application
metadata module imported by the project config. The configuration layer drives
discovery; it does not reinterpret handler bodies.

### Field profiles and drivers

Field profiles own widget-level operations, parts, value codecs, option
projection, loading/error assertions, and serializable readiness capabilities.
They do not own form-instance relationships such as “product filters caseType.”

The effect graph connects stable form nodes and references profile capabilities.
Executable generic or application drivers implement validated capabilities but
do not declare new semantic edges.

### Compiler, schema, and MCP

The trusted compiler receives normalized fields already mapped to stable
contract IDs, runs configured scenarios, validates application effects, and
serializes evidence/diagnostics. The schema and MCP layers receive data only;
they never receive Angular components, callbacks, services, or executable
drivers.

## Recommendation

Approve the high-level architecture, then use this delivery order:

1. Finish the project-aware configuration foundation and stable contract-node
   mapping.
2. Approve the public separation among actionable effects, dependency
   scaffolds, opaque signals, and analysis completeness.
3. Implement strict runtime schemas, canonical serialization/hashing, endpoint
   and capability validation, readiness validation, and deterministic SCC
   diagnostics for explicit effects.
4. Add nested/repeater-relative source normalization before enabling string
   scaffolding in production.
5. Add controlled scenario evidence as a separate non-authoritative producer.
6. Add runtime/browser conformance only after readiness and observation schemas
   are approved.

Do not infer operational effect verbs from callback names, function bodies,
field proximity, one differential, or one browser trace.

## Confidence and usefulness

| Claim | Confidence | Rationale |
| --- | ---: | --- |
| Framework metadata cannot expose arbitrary operational effects | 0.95 | Public and pinned surfaces contain no semantic source-target-kind graph |
| Explicit per-form effects cover the ordering issues encountered | 0.90 | Candidate shape represents trigger, target, kind, timing/readiness, and order |
| Conservative direct-string scaffolds are useful | 0.70 | Negative cases are now covered; relative scope normalization remains |
| Opaque behavior can be surfaced safely without execution | 0.95 | Functions, Observables, handlers, hooks, validators, and dynamic arrays remain unknown |
| Controlled scenario deltas aid review/conformance | 0.75 | Real builder test proves deltas but not causality or global coverage |
| Automatic operational-verb inference is reliable | 0.20 | Application semantics dominate and reviews found many false-positive paths |
| Combined configuration + profiles + explicit effects can cover most encountered cases | 0.85 | Ownership is coherent; corpus and browser/async gates remain |

The major usefulness is not high automatic inference coverage. It is a scalable
authoring path: declare a relationship once per form relationship, reuse the
field profile across all instances, and let conservative evidence highlight
missing or drifting declarations.

## Limitations

- The analyzer is a bounded research utility, not a production JavaScript
  evaluator or symbol resolver.
- It requires normalized stable node IDs and does not traverse nested fields.
- It does not resolve field-relative model/form-state paths.
- It reports ancestor propagation and dynamic arrays as unknown rather than
  calculating descendant effects.
- Scenario equality accepts only JSON-like values plus explicit `undefined`;
  runtime objects are rejected.
- Graph validation reports SCC members but does not prove convergence or assign
  final severity.
- No async provider, network request, error, cancellation, race, Formly
  `fieldChanges` trace, or browser experiment was executed.
- No production/workplace coverage percentage is claimed.

## Unresolved maintainer questions and next gate

Before implementation, the maintainer should approve:

1. first-class DTO boundaries for declared effects, dependency scaffolds,
   opaque signals, and completeness;
2. stable node/reference and repeated-row semantics;
3. relative source-path normalization;
4. effect/profile precedence and condition-rule references;
5. cycle severity and convergence policy;
6. readiness capability vocabulary and async error semantics;
7. configuration contribution and version/hash rules; and
8. browser conformance scope.

The first implementation slice should contain explicit-effect schema and
validation only. String analysis and scenario/browser evidence remain separate
follow-on producers.
