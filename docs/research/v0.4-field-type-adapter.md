# v0.4 Field-Type Adapter Research

**Scoped status:** Expanded prototype complete; architecture decision ready;
public DTO approval pending

## Executive conclusion

Formly's type registry can identify the Angular component, inherited type,
default options, and wrappers associated with a custom type. It cannot describe
the component's rendered accessibility roles, interactive parts, model-value
codec, option API, or operating sequence. Inspecting a component class or
template cannot reliably fill that gap because Angular templates may delegate
to child components and change with props, state, lifecycle, or overlays.

**Decision:** proceed with an Angular-assisted adapter authoring pipeline, but
do not treat Angular metadata or template analysis as the interaction contract.
Use a hybrid model:

1. an application-owned, serializable contract-adapter registry declares each
   custom type's semantic and interaction profile;
2. the compiler emits the resolved profile and its provenance on each node;
3. a separate, application-owned driver registry binds profile `driverId`s to
   executable Playwright behavior when generic operations are insufficient;
4. Formly's runtime registry supplies inventory, inheritance, defaults, and
   wrapper composition, but never invents interaction semantics; and
5. a later rendered harness verifies declared roles and parts with observed
   evidence rather than silently generating authoritative profiles.

This preserves the core rule: the agent emits typed intent against a node and
value; it never writes selectors or widget-specific Playwright code.

Angular can automate much of the adapter-authoring work. Its public reflection
API provides exact but shallow component metadata, its compiler can produce
derived template candidates when source is available, and an Angular render
harness can capture observed scenario behavior. These tiers should feed a
scaffold-and-verify pipeline rather than silently manufacture semantic truth.

The prototype supports a **go** decision for registry inventory, source
analysis, review scaffolds, and the feasibility of rendered conformance. It
supports a **no-go** decision for replacing declared profiles with automatic
inference. The recommended first production slice is therefore an authoring
tool plus a small declared profile registry, not a larger parser that promises
to understand
arbitrary Angular components.

## Decision packet

### Question and owner

How should Formly Contract learn enough about application-specific field types
to produce reliable test intent and Playwright execution metadata?

The repository maintainer owns the decision. This research does not authorize
a public schema or runtime dependency change.

### Why the answer matters

An opaque type string proves only which Formly registration key a field uses.
Treating a name such as `cool-radio-btn-grp` as a button, radio group, or any
other widget creates exactly the selector and interaction guessing that the
contract is intended to eliminate.

### Scope and prohibited actions

The comparison covers declared profiles, Formly registry inspection, component
or template inspection, and rendered observation. It uses the repository's
synthetic custom types only. It does not copy workplace source, parse function
text, expose Angular internals as contract API, or implement production
Playwright drivers.

### The value-domain finding

The rendered rating case is the strongest proof that DOM scraping is not a
model-value contract. The five radio options have accessible names `1` through
`5`, and selecting the radio named `4` changes the model to numeric `4`.
However, the same radio element reports native DOM value `"on"` and an empty
name. Static analysis can see `[value]="rating"`, but cannot generally prove
the runtime type or label-to-model mapping.

Therefore possible values should be sourced in this order:

1. existing static Formly options, which v0.3 already projects;
2. a reviewed adapter projection for a custom field's JSON-safe option API;
3. values observed in a controlled, explicitly configured scenario, marked
   scenario-complete rather than globally complete; or
4. an explicit unknown with a runtime enumeration strategy.

Automatically clicking every option to reverse-engineer model values is not a
safe general build step: actions may trigger application effects, dependent
loads, or irreversible workflows. Such probing belongs only in an isolated
application-provided harness with synthetic providers.

### What the build tool can reliably automate

The successful automatic boundary is:

- enumerate loaded Formly aliases, components, inheritance, defaults, and
  wrappers;
- reflect exact Angular selector/input/output/projection metadata;
- resolve inline and external source templates;
- parse native elements, literal roles/input types, bindings, events,
  control-flow, and referenced child selectors;
- collect custom `props` paths from template and component TypeScript;
- propose narrow generic-driver candidates for recognizable native-backed
  controls;
- emit review-required adapter stubs with explicit unknowns; and
- compare reviewed declarations with rendered role/name/part observations.

It cannot reliably determine:

- the DOM/ARIA produced inside an opaque child component;
- the intended semantic operation when several actions exist;
- label-to-model codecs or every legal value;
- overlay, portal, focus, keyboard, or loading sequences from shallow source;
- behavior hidden behind services, lifecycle, or runtime state; or
- which harness methods or component methods are safe semantic operations.

Those limits are intrinsic information boundaries, not missing Angular APIs.

## Expanded interaction-profile matrix

The adversarial review agreed with the automatic-inference no-go and the
profile/driver ownership split, but correctly found that the first spike had
not exercised the full profile vocabulary or retained automated browser
conformance. A second matrix now covers the missing interaction families.

### Serializable profile prototype

`field-type-profile.spike.ts` and its tests define and validate a candidate
framework-independent registry containing:

- semantic type and scalar/array/object model shape;
- named interactive parts with expected roles and cardinality;
- closed interaction kinds for fill, choice, autocomplete, row selection, and
  repeater access;
- projected, scenario-runtime, unknown, and not-applicable value domains;
- compatible generic driver IDs or a namespaced application driver ID/version;
- explicit type registrations and named field variants;
- ordered wrapper parts and activation preconditions; and
- a canonical registry hash that is insensitive to registration order but
  changes when a profile version changes.

The validator rejects missing parts, missing profile references, duplicate
registrations, incompatible generic drivers, and unstable application driver
IDs. Resolution fails early for unmapped Formly types, variants, and wrappers.
This is a retained research API, not an approved v0.4 DTO.

### Generic versus application driver gate

A reviewed profile may use a generic driver only when:

1. its interaction kind is in the closed generic vocabulary;
2. every required semantic part has a declared role/locator contract;
3. its value domain has a declared projection or is explicitly runtime-
   enumerable for the scenario;
4. wrapper prerequisites are themselves declared ordered preconditions; and
5. no additional application-specific state transition or model codec is
   needed.

Use an application driver when a portal or overlay cannot be scoped by the
generic parts, keyboard/focus mechanics are component-specific, selecting an
option requires business actions, the UI/model codec needs executable logic,
or the component's supported operation cannot fit the closed vocabulary.

### Reconciled decision levels

- **Approved architectural principle:** arbitrary custom fields remain non-
  actionable without a reviewed semantic profile; Angular discovery produces
  evidence and stubs, not authority.
- **Supported production direction:** serializable profiles, validated generic
  driver bindings, allowlisted application drivers, explicit variants/wrapper
  preconditions, and deterministic registry identity.
- **Candidate requiring schema review:** the exact DTO names and whether every
  interaction/value-domain branch belongs in the first v0.4 slice.
- **Still unproven:** automated browser conformance in repository CI, coverage
  percentages on the workplace component corpus, lazy feature-injector
  inventory, and reuse of any application CDK harnesses.

## Evidence

### Documented facts

1. Formly custom types associate a type alias with an Angular component. The
   custom component owns its template, and the field config may refer to the
   component or the registered string alias. Source:
   <https://v6.formly.dev/docs/guide/custom-formly-field/>
2. Formly's `TypeOption` API exposes `name`, `component`, `defaultOptions`,
   `extends`, and `wrappers`; it has no accessibility or interaction contract.
   `FormlyConfig` exposes `getType` and maintains registered types. Source:
   <https://v6.formly.dev/docs/api/core/>
3. Formly documents `props` as template-specific options whose required shape
   is defined by the particular template implementation. Source:
   <https://formly.dev/docs/guide/properties-options/>
4. Playwright recommends user-facing locators and explicit contracts such as
   roles, labels, and test IDs. Source: <https://playwright.dev/docs/locators>
5. ARIA roles imply different structures and interaction patterns. A radio
   group owns `radio` elements, while a combobox may control a listbox, grid,
   tree, or dialog popup and may or may not accept free text. Sources:
   <https://www.w3.org/WAI/ARIA/apg/patterns/radio/> and
   <https://www.w3.org/WAI/ARIA/apg/patterns/combobox/>.
6. Angular's stable `reflectComponentType` API exposes a component's selector,
   inputs, outputs, content selectors, and standalone status. It does not
   expose the component template or rendered DOM. Sources:
   <https://angular.dev/api/core/reflectComponentType> and
   <https://angular.dev/api/core/ComponentMirror>.
7. Angular 20's public `@angular/compiler` entry point exports `parseTemplate`,
   which parses template text into an Angular template AST. The installed
   declaration describes it as parsing template text into render3 nodes and
   metadata with no other dependencies.
8. Angular warns that full Ivy instructions are not public API and may change
   between patch versions. A build tool should use public reflection/compiler
   APIs and source templates rather than inspect private `ɵcmp` instructions.
   Source: <https://angular.dev/tools/libraries/creating-libraries>.
9. Angular CDK component harnesses are component-author-owned interaction APIs
   designed to hide DOM internals and work across test environments. Alternate
   environments require a `HarnessEnvironment` implementation. Source:
   <https://material.angular.dev/cdk/testing/overview>.
10. Current Playwright component testing uses an application-owned story
    gallery served by the application's own build pipeline. Components execute
    in a real browser and Playwright supplies normal locators, clicks, retries,
    and tracing. This supports a small Angular-owned observation gallery without
    requiring Playwright to understand Angular compilation. Source:
    <https://playwright.dev/docs/test-components>.

### Repository observations

1. `FormlyConfig.types` is publicly readable in Formly 6.1.8. The prototype
   records the raw declaration before calling `getType`, separately records the
   inherited component/wrappers, and uses a controlled `getMergedField` input
   to report the effective inherited default-option and prop keys.
2. `TypeOption` still contains no rendered DOM or model-codec information.
3. Resolving component instance defaults requires a view container and
   injector; a controlled builder without rendering cannot inspect actual DOM.
4. The synthetic `rating` type renders multiple radios and derives legal
   values from `props.min`/`props.max`, while its Formly registration contains
   only `{ name, component }`.
5. The synthetic `repeat-section` type exposes add/remove actions that are not
   present in its field config or Formly registration.
6. The existing `deriveLocators` callback already establishes a useful safety
   pattern: application code runs only during trusted compilation, receives an
   immutable narrow input, returns strictly validated data, and never enters an
   MCP/query boundary.
7. The exact installed Angular 20.3.29 compiler publicly exports
   `parseTemplate`; its AST includes elements, attributes, bound attributes,
   events, control-flow blocks, and child component nodes.
8. Public Angular reflection successfully inventories the real `currency`,
   `rating`, and `repeat-section` Formly registrations without private Ivy
   inspection.
9. The retained source analyzer handles both inline templates and literal
   external `templateUrl` resources supplied by a build-time loader.
10. The deterministic scaffold correctly proposes `fill`/`spinbutton` for the
    native-backed currency field and `check`/`radio` for rating, while retaining
    possible values as unknown.
11. The same scaffold refuses to assign an operation to a repeater with both
    add and remove actions or to a component composed only from opaque child
    selectors.
12. Browser observation found one accessible `group` named `Condition rating`,
    zero `radiogroup` roles, and five `radio` roles. This proves that a plausible
    declared container role may still drift from the real surface.
13. Checking the radio named `4` updated the Formly model to number `4`, even
    though the radio's DOM value was `"on"`. DOM attributes do not prove the
    custom field's model codec.
14. Clicking `Add defect` increased the rendered repeater rows from one to two,
    confirming that observed behavior can validate a declared operation but
    does not tell the compiler whether that operation is the desired test step.
15. A real inherited `rating-compact` registration resolves the base rating
    component while retaining its declared `extends`, wrapper, and default-
    option surface in the inventory report.
16. The expanded registry prototype represents the five complex interaction
    families, an application-driver overlay variant, named variant selection,
    ordered wrapper activation contributions, early unmapped failures, and
    deterministic hashing.
17. The static generator derives a button-radio candidate but preserves
    multi-step overlay, autocomplete, row-selection, and expandable-repeater
    sequences as unknown until a profile is reviewed.
18. Manual browser execution verified the expanded matrix's expected roles,
    dynamic options, structured autocomplete value, row-array model update, and
    repeater expansion/add effects.

### Inferences

1. Booting `FormlyConfig` improves discovery and default resolution but cannot
   make custom fields operationally self-describing.
2. Static Angular component/template inspection would be an unreliable source
   of interaction truth because child components, structural control flow,
   overlays, and runtime props can change the rendered surface.
3. DOM observation can verify roles, names, parts, and visible options for a
   scenario, but it cannot always infer the intended model codec, legal
   off-screen states, or the safest action sequence.
4. Therefore neither registry inspection nor observation replaces explicit
   application semantics; they complement it.
5. Angular reflection and template analysis can remove most adapter boilerplate
   and identify suspicious gaps, but their output should be tagged `derived`
   until a human declaration or rendered observation confirms it.
6. A reviewed generic profile is sufficient for custom components whose
   rendered accessibility surface maps cleanly to a standard Playwright action.
7. Composite and opaque-child components still need an explicit profile and,
   when generic operations cannot express their sequence, an allowlisted custom
   driver.
8. Rendered observation should be a CI conformance layer because it caught a
   real `group` versus `radiogroup` mismatch that static intent could easily
   overlook.

### Residual unknowns for production design

- Whether a type-level static profile covers enough real custom fields or a
  deterministic field-level variant mechanism is required in the first slice.
- How wrapper-provided behavior should compose when a wrapper adds expansion,
  dialogs, or locator scope around an otherwise standard type.
- Which generic operation vocabulary covers the target applications before a
  custom driver is required.
- Whether component-reference field types need first-slice support or may
  initially require stable string aliases.
- How feature- or route-scoped Formly registries should be enumerated so lazy
  injectors do not produce a falsely complete inventory.
- Whether the target application already has CDK harnesses that can be reused
  for conformance without introducing a Playwright harness environment.

## Options compared

| Option | Strengths | Failure modes | Recommendation |
| --- | --- | --- | --- |
| Guess from the type name | Zero setup | Confidently wrong for arbitrary application names | Reject |
| Read `FormlyConfig` only | Enumerates registered names, components, defaults, inheritance, wrappers | No roles, parts, option API, codec, or actions | Use for inventory only |
| Statically inspect Angular components/templates | May find literal roles or elements | Compiled/dynamic templates, child components, props, overlays, and lifecycle make it incomplete and framework-coupled | Do not use as authority |
| Application-declared adapter profiles | Deterministic, reviewable, cheap, works without browser | Requires application maintenance; declarations may drift | Primary source of truth |
| Render and observe DOM | Highest fidelity for a supplied scenario | Heavy; scenario-specific; cannot infer every semantic or driver behavior | Conformance and parity layer |
| Generate raw Playwright from metadata | Simple for standard controls | Metadata cannot express every application-specific sequence safely | Use generic drivers only |
| Profile plus allowlisted driver binding | Handles both standard and truly custom widgets while retaining typed intent | Requires versioned application driver code | Recommended hybrid |
| Angular reflection + template AST | Automatically inventories public component API and literal template semantics | Cannot prove runtime branches, child internals, overlays, model codec, or intended operation | Use to scaffold profiles |
| Existing Angular CDK harness | Already provides a supported interaction abstraction | Optional, method vocabulary is component-specific, and Playwright needs an environment/binding | Reuse when available |

## Recommended architecture

### 1. Keep Formly and contract registration separate but colocated

Define the custom component, its Formly registration, and its contract adapter
near each other, then compose both registries in the application-owned contract
entry point. Do not add non-Formly properties to `TypeOption` or depend on
Angular private component metadata.

```ts
export const coolRadioContractAdapter = defineFieldTypeAdapter({
  id: 'example.cool-radio',
  version: 1,
  formlyType: 'cool-radio-btn-grp',
  semanticType: 'single-choice',
  valueShape: 'scalar',
  interaction: {
    kind: 'choice',
    containerRole: 'radiogroup',
    optionRole: 'radio',
    operation: 'select-option',
    target: 'option',
  },
  choices: {
    collectionPath: 'props.options',
    labelPath: 'label',
    valuePath: 'value',
    disabledPath: 'disabled',
  },
  driver: { id: 'generic.role-choice', version: 1 },
});
```

The exact DTO remains subject to schema review, but it should be serializable,
strictly validated, and framework-independent.

### 2. Separate semantic profiles from executable drivers

The contract adapter describes what the field means and which typed operations
it supports. A future Playwright driver registry describes how to execute those
operations.

- Standard profile + standard roles: use a generic built-in driver.
- Composite or unusual profile: bind an application driver such as
  `example.address-lookup@2`.
- Contract artifacts contain only the driver ID/version and validated
  parameters—not functions or source text.
- Driver resolution occurs from an application allowlist during trusted test
  compilation/execution; an agent cannot select an arbitrary module.

This means an agent requests something like `setChoice(nodeId, value)`. The
validated node profile selects the driver; the agent never supplies
`getByRole(...)`, CSS, XPath, or overlay mechanics.

### 3. Model composite parts and locator requirements explicitly

A profile names semantic parts such as `input`, `option`, `start`, `end`,
`trigger`, `popup`, `row`, `addItem`, or `expandItem`. Node-local locators bind
to those names. The profile declares which parts are required for each
operation, allowing contract validation to reject a test intent before
Playwright times out.

### 4. Let adapters project custom prop APIs

Custom fields often store choices outside `props.options` or use different
label/value properties. The profile needs a constrained property projection,
not unrestricted object serialization. Static JSON-safe property paths should
cover the first slice; a narrow trusted derivation callback can be considered
later if the production acceptance matrix proves it necessary.

### 5. Compose type and wrapper semantics

Custom wrappers can add required actions such as expansion, dialogs, or a
different locator scope. The registry should therefore support both type
profiles and wrapper contributions. The prototype proves only direct type
registration, selection of a named variant, and wrapper contributions applied
in declared wrapper order. It does not implement Formly profile inheritance or
settle whether a field variant overrides wrapper semantics.

The following five-layer precedence is therefore an **unproven design
proposal**, not a spike result:

1. built-in semantic defaults;
2. inherited Formly type profile;
3. named application type profile;
4. wrapper contributions in declared wrapper order; and
5. an explicit field-level variant, if the spike approves one.

Conflicts must be diagnosed rather than last-write-wins silently.
Maintainer approval and focused conflict tests are required before this order
becomes a public contract.

### 6. Make missing profiles actionable

An unmapped non-built-in type should receive a stable diagnostic such as
`UNMAPPED_FIELD_TYPE`. Its contract node retains structure and declared props
already on the allowlist but advertises no invented interaction. Typed test
intent targeting that node fails early with a message that names the missing
type adapter.

The application compiler may use `FormlyConfig.types` to emit an inventory of
registered types and report which lack adapters. A scaffold command can create
reviewable adapter stubs, but must not guess their completed semantics.

### 7. Add observed conformance later

A controlled Angular harness renders representative scenarios and captures
roles, accessible names, target counts, and visible options. It compares those
observations with the declared profile:

- matching facts may receive separate observed evidence;
- mismatches fail or warn during CI according to policy; and
- observations never silently rewrite the declared adapter.

This turns profile drift into a test failure while preserving the distinction
between author intent and rendered ground truth.

### 8. Add an Angular-assisted adapter generator

The application-owned Angular generation host can combine four sources:

1. **Formly registry inventory:** `FormlyConfig` resolves type alias,
   component, inheritance, default options, and wrappers in the configured
   application injector.
2. **Stable Angular reflection:** `reflectComponentType` records selector,
   input/output aliases, content projection selectors, and standalone status.
3. **Source analysis:** TypeScript analysis locates the component decorator and
   custom props interface; `parseTemplate` extracts candidate native elements,
   literal roles/input types, bindings, events, control-flow branches, and
   referenced child selectors.
4. **Rendered observation:** TestBed or the browser harness mounts synthetic
   scenarios and captures roles, names, visible parts/options, and overlay
   behavior.

The generator produces two artifacts:

- an inventory/conformance report containing all raw findings and evidence;
  and
- a minimal adapter scaffold with only defensible defaults filled in and
  explicit TODOs for model codecs, operations, dynamic states, and driver
  bindings.

Only the reviewed adapter profile enters the semantic contract. Discovery
details such as Angular selectors and component inputs stay in the build report
unless they are needed as validated operational metadata.

Suggested evidence rules:

| Source | Evidence | What it may establish |
| --- | --- | --- |
| Formly registration | `declared` | type/component/default/wrapper relationship |
| `reflectComponentType` | `declared` | selector and Angular input/output surface |
| Template AST | `derived` | candidate parts, literal roles, prop paths, and events |
| Rendered harness | `observed` | actual scenario roles, names, parts, and visible options |
| Reviewed adapter | `declared` | semantic type, model codec, supported operations, driver binding |

The tool should flag rather than guess when it sees dynamic role bindings,
unknown child components, overlays, template outlets, or a custom prop used in
an event path. It should also report registered Formly types that were not
loaded into the generation injector, since lazy feature injectors can make a
single root inventory incomplete.

### 9. Reuse component harnesses when present

If a custom component already ships an Angular CDK `ComponentHarness`, that is
strong evidence of its supported consumer interaction API. The build tool can
detect a separately registered harness binding and reuse it in conformance
tests or a future driver adapter. It should not infer typed operations merely
from arbitrary harness method names.

A direct Playwright harness environment is possible, but it is a larger
integration commitment. The first slice should instead reuse harnesses inside
Angular TestBed for profile verification and keep the Playwright driver binding
explicit. A later spike can compare a Playwright `HarnessEnvironment` with the
smaller contract-driver abstraction.

## Proposed delivery slices

### Production gate from this spike

Proceed with the following constraints:

1. Keep Angular/TypeScript discovery in a trusted build-time authoring path;
   do not add compiler analysis to the schema package, MCP server, or routine
   query path.
2. Generate a report and review-required adapter stub, never an automatically
   approved profile.
3. Use only public Angular reflection/compiler entry points and source files;
   reject private `ɵcmp` disassembly.
4. Preserve each fact's source independently: Formly registration, Angular
   reflection, template derivation, reviewed declaration, or rendered
   observation.
5. Require a declared profile before a custom type becomes agent-actionable.
   An unmapped or ambiguous component remains discoverable but non-operable.
6. Use generic drivers only when the reviewed profile maps to a closed,
   validated operation vocabulary and supplies required parts plus an explicit
   label-to-model-value projection for value-bearing operations. The spike's
   generic bindings are candidate hypotheses until production validation also
   proves node-local locator completeness, model codecs, wrapper prerequisites,
   driver versions, and allowlist membership. Bind composite behavior through
   a stable, allowlisted application driver ID/version.
7. Treat observed option names as scenario evidence. Do not equate DOM `value`
   attributes with model values unless a declared codec proves that mapping.

The first production implementation should cover `currency`, `rating`, and
`repeat-section` as the acceptance matrix. It should also retain the synthetic
opaque-child case as a negative test so later heuristics cannot silently turn
unknowns into guessed operations.

### Slice A: Declared profiles

- serializable type-profile DTO and strict validation;
- application-supplied registry keyed by stable Formly type string;
- built-in profiles for currently supported synthetic types;
- choice projection from constrained prop paths;
- composite part and generic operation metadata;
- unmapped-type diagnostics and registered-type inventory; and
- adapter identity/version included in deterministic output or bundle inputs.

### Slice A0: Angular-assisted inventory and scaffolding

- configured `FormlyConfig` inventory from the application generation host;
- stable `reflectComponentType` metadata;
- optional source-template and custom-props analysis;
- evidence-tagged adapter stub generation;
- unmapped and dynamically ambiguous findings; and
- no private Ivy metadata dependency.

### Slice B: Wrapper composition and variants

- wrapper interaction contributions;
- deterministic type inheritance;
- field-level variants selected only from JSON-safe discriminators; and
- conflict diagnostics.

### Slice C: Driver bindings

- typed operation vocabulary;
- generic role/test-ID drivers;
- allowlisted application driver IDs and versions; and
- intent validation that proves required targets and values exist before
  execution.

### Slice D: Observed conformance

- rendered synthetic harness;
- accessibility/part capture for representative states;
- declared-versus-observed diff; and
- CI drift policy.

## Confidence and next gate

Confidence is **high** in the ownership split and in the feasibility of Angular-
assisted inventory, source analysis, and deterministic review scaffolds. Those
claims are backed by executable tests against the pinned Angular/Formly stack.
Confidence is also high that browser observation can expose drift and model
effects, based on direct synthetic-app execution;
automating that conformance in repository CI remains separate work.

Confidence is **medium-high** that the candidate interaction vocabulary can
represent the tested families, and **medium** in the current generic-versus-
application driver eligibility rules. The retained matrix now covers native-
backed controls, a conditional overlay, autocomplete with a structured value,
row selection, expandable repeaters, external templates, opaque children,
explicit variants, wrapper preconditions, inheritance, and registry hashing.
The candidate runtime checks now reject interaction/driver mismatches, missing
parts and profiles, duplicate registrations, invalid application-driver IDs,
and generic value-bearing drivers without a declared label-to-model-value
projection. They are not a strict public DTO parser and do not yet validate
node locators, codecs, wrapper capability, driver allowlists, or all identity
constraints. Confidence remains medium on the exact public DTO names and
workplace-corpus coverage, and low on lazy feature-injector completeness until
tested.

The research question is resolved: Angular can substantially reduce authoring
effort, but it cannot make arbitrary custom Formly components self-describing.
The next gate is maintainer approval of the profile DTO and precedence rules,
followed by a strict runtime schema and generic-driver capability gate in the
combined Slice A0/A implementation. The retained complex-widget matrix should
become the acceptance fixture for that review. Automated browser conformance
and any application CDK harness integration can proceed as a later slice
without weakening the declared-profile requirement.
