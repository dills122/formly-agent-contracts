# v0.3 Test Locator Specification

## Objective

Add deterministic, evidence-tagged DOM locator metadata to form contract nodes
so Cypress, Playwright, and later driver packages can target controls without
inventing selectors or searching application source manually.

The primary user is an E2E author or coding agent consuming a compiled form
contract. Success means the contract reports exact declared test attributes,
supports application-specific derived conventions, and can describe composite
widgets with several interactive DOM targets.

## Contract model

Schema version `0.3.0` adds a required ordered `locators` array to every node.
An empty array explicitly means that no reliable locator is known.

Each locator contains:

- `target`: a stable node-local identifier such as `control`, `start`, or
  `end`;
- `strategy`: `testId`, `role`, `label`, `placeholder`, or `domId`;
- `value`: the attribute value, role, label, placeholder, or DOM ID;
- `attribute`: required only for `testId`, so conventions such as
  `data-testid`, `data-test`, `data-cy`, and `data-pw` remain portable;
- `accessibleName`: optional for role locators;
- `evidence`: `declared`, `resolved`, or `observed`; and
- `confidence`: `exact` when read directly from that evidence source, or
  `derived` when produced by a convention.

Locators live on the semantic node because node-level discovery is the common
query path. Multiple entries with different `target` values represent one
Formly field that renders several interactive elements. Multiple entries for
the same target are ordered fallback strategies.

## Evidence and source-of-truth rules

- `declared`: read from the supplied field configuration before a Formly build.
- `resolved`: read from the controlled post-build field tree.
- `observed`: captured from a real browser DOM by a future observation layer.

Observed evidence is authoritative for what actually rendered. Declared and
resolved entries remain useful pre-browser candidates but must never be
silently relabelled as observed.

`FormlyFormBuilder` does not render DOM and therefore cannot produce observed
evidence. It may resolve expression-driven `props.attributes` and Formly field
IDs, which remain resolved configuration evidence.

## Adapter behavior

The adapter automatically projects:

1. exact test attributes from `props.attributes` for the configured attribute
   allowlist, defaulting to `data-testid`, `data-test-id`, `data-test`,
   `data-cy`, and `data-pw`;
2. explicit or Formly-generated field IDs as lower-confidence `domId`
   candidates; and
3. explicit placeholder and role/accessible-name metadata only when the
   relevant value is present in the field configuration.

The extraction input may provide an opt-in `deriveLocators` function. It
receives only immutable, JSON-safe identity data: form ID, node ID, model path,
key path, position, evidence, field ID, Formly type, and semantic type. It does
not receive the live Formly field. Its outputs are always tagged `derived` and
may describe multiple targets. A throw or malformed result becomes a stable
`LOCATOR_DERIVATION_FAILED` diagnostic.

The adapter never derives CSS or XPath selectors and never executes functions
found inside Formly configuration to obtain locators. MCP/query paths read
compiled artifacts and never invoke the derivation function.

## Code style

Public shapes use readonly data and discriminated string literals:

```ts
const locator: ContractLocator = {
  target: 'start',
  strategy: 'testId',
  attribute: 'data-testid',
  value: 'coverage-period-start',
  evidence: 'declared',
  confidence: 'exact',
};
```

Projection order is deterministic: exact test IDs, derived locators, explicit
role/placeholder candidates, then DOM ID fallback. Exact duplicate locators
are removed without changing the first occurrence.

## Testing strategy

- Schema tests accept representative strategies, composite targets, and
  observed evidence, and reject malformed conditional fields.
- Adapter tests prove exact `props.attributes` extraction, no-locator honesty,
  convention-agnostic derivation, composite targets, deterministic de-duplication,
  and failure diagnostics.
- The component-free Formly test proves an expression-resolved test attribute
  remains `resolved`, not `observed`.
- Demo and canonical hashing tests prove stable output.

## Boundaries

Always:

- update schema and runtime validation before adapter output;
- retain evidence and confidence on every locator;
- return an empty locator array rather than fabricate a selector; and
- run focused tests, `pnpm check`, clean-clone verification, and review.

Ask first:

- add browser automation or a new public runtime dependency;
- change the default test-attribute allowlist after publication; or
- add locator execution to MCP/query paths.

Never:

- include workplace identifiers or screenshots in committed fixtures;
- claim a builder-resolved locator was observed in a browser;
- serialize CSS/XPath guessed from DOM structure; or
- expose the live Formly field to a derivation callback.

## Success criteria

- Exact declared `data-*` test attributes appear on the correct node.
- An app can derive its own test-id convention without hardcoding that
  convention in the package.
- One node can carry locators for several named interactive targets.
- A field with no reliable information has `locators: []`.
- Resolved attributes retain `resolved` evidence; schema permits future
  `observed` entries without merging them.
- Output remains deterministic and all repository gates pass.

## Open questions deferred beyond v0.3

- Browser capture and declared/resolved/observed parity diagnostics.
- Proving locator uniqueness within a rendered page.
- Typed Playwright/Cypress driver execution and fallback selection policy.
