# v0.4 E2E Authoring Metadata Specification

**Status:** Implemented compatibility boundary. Successor source, journey,
behavior/scenario, context, and driver capabilities are planned as sibling
records under the
[RH-06 reconciliation](planning/agent-context-hardening/rh-06-reconciliation.md)
and
[execution index](planning/agent-context-hardening/execution-index.md).

## Objective

Make a Form Contract describe enough of a field's E2E interaction surface for
an agent to choose a valid value and operate the rendered widget without
inventing behavior. The initial workplace-form evaluation found that the v0.3
contract represented structure honestly, but left test authors to infer widget
roles, dynamic choice handling, cross-field ordering, locator durability, and
repeater activation.

This specification remains the contract for Form Contract `0.4.0`. It is not
the home for RH-04 portable behavior/scenario DTOs, source-lineage or journey
records, agent-context manifests, or executable driver registries. Those begin
as strict sibling record families; folding any stable subset into a later Form
Contract version requires a separate schema decision.

The highest-priority addition is an explicit value domain for choice-like and
finite-domain controls:

- declared static options are complete and enumerable;
- options materialized by a trusted scenario are enumerable for that scenario,
  but are not claimed to be globally complete;
- domains implied by an allowlisted built-in semantic type or declared by an
  application-owned field-type adapter may be enumerated with their source;
- unresolved dynamic or asynchronous choices remain explicitly unknown; and
- the contract never fabricates concrete choices from a custom Formly type
  name, default value, model sample, function body, or remote provider.

## Implemented contract changes

The schema version is `0.4.0`. Existing `options` and `optionSource`
fields remain so consumers can migrate additively. A finite-domain control may
also expose `valueDomain`:

```ts
type ContractValueDomain =
  | {
      kind: 'enumerated';
      source: 'static-options' | 'resolved-options' | 'semantic-type' | 'adapter';
      completeness: 'complete' | 'scenario';
      evidence: ContractEvidence;
      values: readonly JsonValue[];
    }
  | {
      kind: 'dynamic';
      source: 'string' | 'function' | 'async';
      evidence: ContractEvidence;
    }
  | {
      kind: 'unknown';
      evidence: ContractEvidence;
    };
```

`values` contains canonical JSON-safe values. Labels and disabled state remain
in `options`; consumers correlate entries by canonical value. Duplicate option
values are rejected or diagnosed rather than silently collapsed.

Rules for projection:

1. A static option array produces `enumerated`, `static-options`, and
   `complete`, including a deliberately empty array.
2. A trusted scenario that materializes dynamic options produces
   `enumerated`, `resolved-options`, and `scenario`.
3. An unresolved string/function/async option source produces `dynamic` and
   never executes or subscribes during declared extraction.
4. The built-in boolean semantic type produces the complete domain
   `[false, true]` from `semantic-type`.
5. Other built-in or custom types produce no inferred domain unless an
   allowlisted adapter declares one. An adapter domain is `complete` only when
   its projection covers the full declared collection; it is `scenario` when
   the projected collection is limited by the resolved scenario.
6. A default or current model value is a sample, not proof of a domain, and is
   never promoted to `values`.

### Interaction profiles

A node may expose a deterministic `interactionProfile` describing the
rendered role and operation, for example a radio group with radio options, a
select overlay, an autocomplete type-and-pick flow, or a row-selection table.
Profiles come from a small built-in registry or an application-owned adapter
registry passed to the compiler. Custom type names are not mapped by naming
convention.

Reviewed profiles authorize interactive custom controls only. A custom
component whose role is display or assertion-only does not receive an
interaction driver by analogy: v0.4 leaves `interactionProfile` absent, and
successor authoring records must retain an explicit disposition/unknown until
the schema owner approves a non-interactive or no-driver representation.

The minimum profile records:

- the semantic control and option roles when known;
- the operation (`fill`, `check`, `select-option`, `select-from-overlay`,
  `type-and-pick`, or `select-row`);
- named targets for composite widgets; and
- declared adapter provenance.

The artifact is a resolved projection, not a copy of the project-owned
registry. A form records the one registry identity used during extraction, and
each mapped node records the selected profile plus the composed interaction
surface:

```ts
interface ContractFieldTypeProfileRegistryIdentity {
  readonly schemaVersion: '0.4.0';
  readonly id: string;
  readonly version: number;
  readonly contentHash: string;
}

interface ContractInteractionProfile {
  readonly profile: { readonly id: string; readonly version: number };
  readonly semanticType: string;
  readonly valueShape: 'scalar' | 'array' | 'object';
  readonly evidence: 'declared';
  readonly parts: readonly FieldTypeProfilePart[];
  readonly interaction: FieldTypeProfileInteraction;
  readonly driver: FieldTypeProfileDriver;
  readonly effectCapabilities: {
    readonly targetProperties: readonly (
      | 'enabled'
      | 'options'
      | 'required'
      | 'value'
      | 'visibility'
    )[];
    readonly readiness: readonly {
      readonly id: string;
      readonly targetProperty:
        | 'enabled'
        | 'options'
        | 'required'
        | 'value'
        | 'visibility';
      readonly evidence: 'declared';
    }[];
  };
  readonly preconditions: readonly FieldTypeWrapperPrecondition[];
  readonly unknowns: readonly {
    readonly scope: 'profile' | 'wrapper';
    readonly source: string;
    readonly aspect: FieldTypeProfileUnknownAspect;
    readonly reason: string;
    readonly evidence: ContractEvidence;
  }[];
  readonly provenance: readonly string[];
}

interface ContractNode {
  // Existing v0.3 fields remain unchanged.
  readonly valueDomain?: ContractValueDomain;
  readonly interactionProfile?: ContractInteractionProfile;
}

interface FormContractDraft {
  readonly schemaVersion: '0.4.0';
  readonly fieldTypeProfileRegistry?:
    ContractFieldTypeProfileRegistryIdentity;
  readonly crossFieldEffectRegistry?: {
    readonly schemaVersion: '0.4.0';
    readonly id: string;
    readonly version: number;
    readonly contentHash: string;
  };
  readonly declaredEffects?: readonly DeclaredCrossFieldEffect[];
  readonly effectAnalysis?: {
    readonly completeness: 'complete' | 'incomplete';
    readonly reasons: readonly (
      | 'declared-partial'
      | 'effect-cycle'
      | 'form-not-declared'
      | 'invalid-declared-effect'
      | 'opaque-dynamic-rule'
      | 'opaque-diagnostic'
    )[];
  };
  // Existing formId, nodes, and diagnostics fields remain unchanged.
}
```

`fieldTypeProfileRegistry` is present whenever a project registry participated
in extraction, including when a particular custom type was unmapped. This lets
the workspace index prove which configuration was considered without repeating
the complete registry on every node. `interactionProfile` is present only when
resolution succeeds. Its parts include wrapper-contributed parts, its
preconditions are in wrapper application order, and its unknowns retain their
profile or wrapper scope. The projection contains data only: Angular component
classes, callbacks, providers, and application-driver implementations never
enter the artifact.

The node's existing `semanticType` records the resolved profile semantic type.
Registry validation and projection must prevent the node semantic type from
contradicting its selected profile. The complete driver reference is retained
so a later typed-intent layer can distinguish a supported generic driver from
an application driver that requires separately registered executable support.

Generic repeater expansion requires both a many-cardinality `button` expansion
part and a many-cardinality `group` item part. Wrapper activation
preconditions are similarly surface-checked: `click` targets one `button`, and
`check` targets one `checkbox` or `radio`. A declaration that names a part but
cannot drive its declared role/cardinality is rejected during registry
validation.

Generic drivers also enforce the model shapes implied by their mechanics:
`fill` is scalar-valued, while row selection and repeaters are array-valued.
Choice and autocomplete shapes may vary because their declared projection maps
the selected option to its model value. Profiles that need a different codec
must use an application driver or retain a blocking `model-codec` unknown.

At the resolved artifact boundary, generic choice, autocomplete, and row
selection profiles require an enumerated node `valueDomain`. Every enumerated
model value must have exactly one corresponding label in the node's `options`,
every option must map back to exactly one enumerated domain value, and one
visible label cannot identify multiple mapped values. Visible-label ambiguity
is checked after trimming and collapsing Unicode whitespace; case remains
significant. An absent, dynamic, unknown, missing, or ambiguous mapping cannot
claim generic executability; projection must omit that generic interaction
profile or use an application driver until a sufficient mapping is available.

### Profile-aware extraction boundary

Declared and trusted resolved extraction accept the canonical registry bundle
produced by project configuration: schema version, registry ID/version,
content hash, and the validated registry data. The adapter verifies that the
claimed identity and hash match the registry before examining fields. A
configured registry identity remains on the form artifact even when no custom
field maps successfully.

An individual field may select one registry-owned named variant through the
root-level, data-only metadata key below:

```ts
{
  type: 'cool-radio-btn-grp',
  formlyContract: {
    profileVariant: 'portal',
  },
}
```

The metadata cannot override roles, parts, operations, drivers, locators, or
value projection. A malformed selector or an undeclared variant leaves the
field non-operable and emits a stable diagnostic.

Every directly declared string wrapper participates in profile resolution in
its declared order. An unregistered, duplicate, malformed, conflicting, or
generic-driver-blocking wrapper leaves the structural node and wrapper names
visible but omits interaction metadata. Wrappers are never assumed transparent
because they may change activation order or locator scope.

Profile and domain failures use stable artifact diagnostic codes:
`UNMAPPED_FIELD_TYPE`, `UNMAPPED_PROFILE_VARIANT`,
`UNMAPPED_WRAPPER_PROFILE`, `DUPLICATE_WRAPPER_REQUEST`,
`PROFILE_PART_CONFLICT`, `WRAPPER_BLOCKS_GENERIC_DRIVER`,
`VALUE_DOMAIN_PROJECTION_FAILED`, and `AMBIGUOUS_VALUE_MAPPING`. Diagnostics
identify the field path and node without copying raw option labels, values,
model data, callback source, or exception details.

### Field effects and ordering

A project may expose a versioned `CrossFieldEffectRegistry` so a test planner
can eventually order interactions. The implemented authoring boundary groups
explicit effects by stable form ID. Each effect has a stable identity/version,
trigger node/event, target node/property, semantic kind, discriminated
timing/readiness, optional condition rule, ordering, and fixed declared,
transparent authority.

```ts
interface CrossFieldEffectRegistry {
  readonly schemaVersion: '0.4.0';
  readonly id: string;
  readonly version: number;
  readonly forms: readonly {
    readonly formId: string;
    readonly coverage: 'complete' | 'partial';
    readonly effects: readonly {
      readonly identity: { readonly id: string; readonly version: number };
      readonly trigger: {
        readonly nodeId: string;
        readonly event: 'selectionChanged' | 'valueChanged';
      };
      readonly target: {
        readonly nodeId: string;
        readonly property:
          | 'enabled'
          | 'options'
          | 'required'
          | 'value'
          | 'visibility';
      };
      readonly kind:
        | 'clears'
        | 'controls-state'
        | 'filters'
        | 'loads'
        | 'toggles';
      readonly timing:
        | { readonly mode: 'sync' }
        | { readonly mode: 'async'; readonly readinessId: string }
        | { readonly mode: 'unknown' };
      readonly conditionRuleId?: string;
      readonly ordering: 'none' | 'source-before-target';
      readonly evidence: 'declared';
      readonly opacity: 'transparent';
    }[];
  }[];
}
```

Field profiles declare an `effectCapabilities` block. `targetProperties`
states which externally-caused changes the profile and its selected driver can
represent. `readiness` names reusable, serializable driver capabilities and
links each capability to the target property it can settle. An async effect's
`readinessId` must match a readiness capability on its resolved target node;
the compiler does not embed or invoke the driver's executable assertion.

Built-in structural controls retain the conservative baseline capabilities
implied by the contract itself: controls can change value, enabled, required,
and visibility state, while controls with a declared option source, an
explicitly dynamic value domain, or a choice/autocomplete/row-selection
interaction can additionally change options.
An enumerated value domain alone does not imply option mutation capability;
for example, a checkbox's `[false, true]` domain is not an option collection.
Custom behavior beyond that baseline must be declared by a resolved profile.

Each per-form registry entry declares `coverage: 'complete' | 'partial'`.
Complete coverage is an author claim, not an inference from edge absence. The
compiler downgrades analysis to incomplete when coverage is partial or when
opaque dynamic rules/diagnostics show that undeclared behavior may remain, or
when the validated effect graph contains a cycle under either cycle policy.
Only effects whose endpoints, target/readiness capabilities, condition rule,
and cycle policy validate are projected into `declaredEffects`.

Strict parsing rejects unknown keys, executable or non-JSON values,
non-declared evidence, opaque authority, malformed or duplicate identities,
async effects without readiness, readiness on non-async effects, and effect
kinds that contradict the target property. Canonical form/effect ordering and
registry hashing make equivalent application declarations byte-stable. Effect
IDs are logical identities scoped to one form; a form cannot activate two
versions of the same effect ID. Root
configuration owns cycle diagnostic severity; the default is `error`.
Duplicate form/effect identities are rejected during strict project-config
parsing with registry/form/effect paths; endpoint and capability failures are
reported later with structured contract diagnostics. Condition references may
name serialized `conditions` only, never opaque `dynamicRules`.

The production implementation includes both the strict declaration format and
compiler resolution. Before an effect enters a form artifact or workspace
index, the compiler resolves its form/node endpoints, serialized condition
rule, target and readiness capabilities, and configured deterministic cycle
policy. The workspace index retains each validated effect's complete trigger,
target, kind, timing, condition, ordering, evidence, and opacity data rather
than identity alone. Invalid or unresolved declarations remain diagnostic
evidence and do not become artifact effects.

Within Form Contract `0.4.0`, only these explicit declarations authorize named
application/business effects such as `loads`, `filters`, `clears`, or
`toggles`. The RH-04 successor design may represent a closed normalized rule
with a witness pinned to its evaluation semantics as a sibling behavior record;
that record can authorize only the exact derived state edge it proves, such as
visibility or required state under one condition. It does not acquire a named
business verb and is not added to the v0.4 DTO.

Other surfaces remain separate non-authoritative or scaffold evidence:

- a change handler, function, Observable, hook, validator, or parser exists but
  its dependencies/effects are opaque;
- a conservative string-expression scaffold references a model/form-state path;
- two controlled scenarios produced different target state; or
- a future runtime/browser trace observed an outcome in visited states.

The v0.4 compiler does not parse function source or promote these evidence
records to `loads`, `filters`, `clears`, or `toggles`. Opaque behavior marks
analysis coverage incomplete, so edge absence cannot prove independence or
unreachability. Browser observations may corroborate a reviewed edge or report
drift, but never create execution authority by themselves.

### Locator durability

DOM ID locators distinguish an author-declared Formly field ID from an ID
generated during a controlled build. An author-declared ID may receive exact
confidence; a generated or application-derived ID remains derived. The
compiler does not claim browser stability from a single observed value.

### Repeaters and nested activation

Array/repeater nodes may expose an adapter-declared item-access profile stating
whether a row must be added, expanded, or otherwise activated before nested
controls can be reached. Generic arrays do not receive an activation hint
without adapter evidence.

## Tech stack and commands

The implementation remains TypeScript in the existing pnpm workspace, using
the strict DTO validator and Vitest coverage already present.

```sh
pnpm --filter @formly-contract/schema test
pnpm --filter @formly-contract/compiler test
pnpm lint
pnpm test
pnpm build
pnpm check:demo
pnpm check:docs
```

No runtime dependency is added by this feature.

## Project structure

- `packages/schema/`: versioned v0.4 DTOs, validation, canonical
  serialization, and schema regressions.
- `packages/compiler/`: value-domain projection, built-in profiles,
  application adapter input, ID provenance, and focused extraction tests.
- `fixtures/synthetic-form/`: public synthetic examples for static, resolved,
  dynamic, boolean, custom-widget, dependency, and repeater cases.
- `apps/demo-cli/`: readable golden v0.4 output and end-to-end assertions.
- `docs/`: contract semantics, migration notes, limitations, and implementation
  status.

## Declared source boundary

Workspace sources normalize every form factory to the same declared extraction
input before the runner invokes the Formly adapter:

```ts
interface DeclaredFormContractInstance {
  readonly fields: readonly object[];
  readonly model?: Readonly<Record<string, unknown>>;
  readonly formState?: Readonly<Record<string, unknown>>;
}

interface FormContractDefinition<TScenario = unknown> {
  readonly id: string;
  readonly create: () => DeclaredFormContractInstance;
  readonly scenarios?: readonly FormContractScenario<TScenario>[];
}
```

Source adapters may translate an application-owned registry or factory map
into this shape. The generic runner does not accept arbitrary instance types or
source-supplied compiler callbacks: it supplies the stable form ID and invokes
the existing declared extractor itself. Trusted resolved-scenario production
is owned by workspace/Angular Task 8 and remains separate from this v0.4
compatibility specification; later consumers carry exact scenario and basis
contract hashes. `fields` is intentionally a framework-neutral array of
configuration objects at the workspace boundary. Task 5.1 performs the
Formly-specific structural handoff inside `compiler`; scalar entries are
rejected here, while deeper Formly validation remains adapter-owned.

## Code style

Use discriminated unions and exhaustive projection rather than optional fields
whose meaning depends on combinations:

```ts
const domain: ContractValueDomain = {
  kind: 'dynamic',
  source: 'function',
  evidence: 'declared',
};
```

Selection policy is intentionally absent from the semantic contract. A future
typed test-intent layer may request `first-enabled` when that policy matches
the test goal, but the field contract only reports what values are known and
how complete that knowledge is.

Every inferred or adapter-declared fact identifies its source. Canonical array
ordering follows source option order; values are never sorted by label.

## Testing strategy

Follow red-green-refactor for each contract behavior:

- schema tests accept every union branch and reject excess, contradictory, or
  non-JSON-safe properties;
- adapter unit tests cover static, empty-static, resolved-dynamic,
  unresolved-dynamic, async, boolean, duplicate, and unsupported custom-type
  domains;
- extraction tests prove callbacks are not invoked and async sources are not
  subscribed;
- adapter registry tests prove application metadata is deterministic and
  allowlisted;
- scenario tests prove resolved domains are marked `scenario`, not `complete`;
- canonical hash tests prove stable output; and
- the synthetic demo proves an agent can distinguish known values from an
  unresolved dynamic choice without proprietary fixtures.

## Boundaries

### Always

- Preserve evidence and completeness separately.
- Treat labels and option data as untrusted application content.
- Keep declared extraction pure and non-mutating.
- Diagnose contradictory adapter metadata and duplicate canonical values.
- Update schema, validation, docs, demo, and tests in the same change.

### Ask first

- Remove or rename v0.3 fields instead of making the v0.4 migration additive.
- Add a runtime dependency or browser/runtime execution boundary.
- Infer relationships by parsing JavaScript or TypeScript function bodies.
- Expand supported Angular or Formly versions.

### Never

- Execute arbitrary callbacks or subscribe to option sources in query paths.
- Treat a type name, default value, or sample model value as a concrete enum.
- Mark scenario-resolved dynamic values as globally complete.
- Copy workplace forms, values, labels, selectors, or business rules into
  repository fixtures or documentation.

## Success criteria

- A static select or radio exposes complete possible values and labels.
- A boolean control exposes the complete `[false, true]` domain.
- A trusted scenario exposes currently resolved dynamic values with scenario
  completeness.
- An unresolved dynamic or asynchronous choice claims no concrete value; a
  typed test intent may separately choose a runtime selection policy.
- An unmapped custom widget exposes no invented domain or interaction profile.
- An application adapter can declare an interactive custom widget's finite
  domain, reviewed interaction profile, effects, and repeater access without
  weakening the core extractor's safety boundary.
- A display- or assertion-only custom component receives no invented driver;
  it remains an explicit disposition/unknown until non-interactive support is
  separately approved.
- Author-declared and generated DOM IDs have distinguishable provenance.
- Runtime validation, canonical hashing, focused tests, the synthetic demo, and
  all repository checks pass.

## Approved implementation decisions

1. v0.4 preserves `options` and `optionSource` additively and introduces
   `valueDomain`; normalization may be reconsidered before 1.0 only through a
   separately approved migration.
2. Application profiles are registered by stable Formly type with explicitly
   named, registry-owned variants. Individual fields may select a declared
   variant through `formlyContract.profileVariant` but may not embed arbitrary
   executable or semantic overrides.
3. Value domains, interaction profiles, locator provenance, repeater access,
   and explicit effects are implemented parts of the v0.4 compatibility
   boundary. RH-04 normalized behavior/scenario DTOs remain successor sibling
   records rather than additions to this version.
4. Artifact provenance records one optional field-type registry identity at the
   form level. Nodes contain only the resolved interaction projection and never
   embed the complete registry or executable Angular/application references.
5. A workspace source factory returns a normalized declared Formly instance.
   Framework- or application-specific source adapters perform normalization;
   the generic runner does not accept an opaque instance plus a compiler hook.
6. Reviewed interaction profiles authorize interactive custom controls.
   Display- and assertion-only components retain absent interaction metadata
   plus an explicit disposition/unknown in successor authoring records until a
   separately approved schema adds non-interactive or no-driver support.
